# stardust landing page — signals experiment

A one-page, single-purpose landing site that tests whether S&P 500 investors will
trade an email for a stock's winning strategy + current buy/sell signal — and
whether they come back.

It is deliberately a **market experiment, not a website**:

- **Frontend:** static HTML/CSS/JS (no framework, no build step).
- **Backend:** one small Flask app that records signups and funnel events to CSV.
- **Analytics:** first-party (your own CSVs), tagged by traffic source. Optional
  PostHog/Plausible hooks in `app.js` if you want more.
- **Demo data:** generated by the real stardust engine, so the prototype numbers
  are honest — see `generate_demo_data.py`.

The experiment design, thresholds, and interpretation rules live in
[`../thermaltrend/VALIDATION_EXPERIMENT.md`](../thermaltrend/VALIDATION_EXPERIMENT.md).

| File | Purpose |

## Run locally

```bash
cd /Users/anilverma/stardust
pip install flask          # gunicorn only needed for production
python landing/server.py   # http://127.0.0.1:8000
```

Regenerate the prototype numbers (run from the repo root, not `landing/`):

```bash
python landing/generate_demo_data.py                     # default 8 tickers
python landing/generate_demo_data.py --tickers AAPL NVDA KO
python landing/generate_demo_data.py --skip-oos          # much faster
```

> The generator imports the `thermaltrend` package and reads its Parquet data, so
> run it on a machine that has the full repo. The **server** does not need any of
> that — it only serves the pre-generated JSON.

## Deploy on AWS

The container is self-contained (Flask + gunicorn + static files). Pick one:

### Option A — EC2 (simplest, cheapest for a 2-week test)

```bash
# on the instance
sudo apt-get update && sudo apt-get install -y python3-venv
git clone <your-repo> && cd <your-repo>/landing
python3 -m venv .venv && . .venv/bin/activate
pip install -r requirements.txt

# run under systemd so it survives reboots
sudo tee /etc/systemd/system/stardust-landing.service >/dev/null <<'EOF'
[Unit]
Description=stardust landing
After=network.target
[Service]
WorkingDirectory=/home/ubuntu/<your-repo>/landing
Environment=LANDING_DATA_DIR=/home/ubuntu/<your-repo>/landing/data
ExecStart=/home/ubuntu/<your-repo>/landing/.venv/bin/gunicorn --bind 127.0.0.1:8000 --workers 2 server:app
Restart=always
User=ubuntu
[Install]
WantedBy=multi-user.target
EOF
sudo systemctl enable --now stardust-landing
```

Put nginx in front for TLS (Let's Encrypt) and proxy `:80/:443` → `127.0.0.1:8000`.
`server.py` honours `X-Forwarded-For` automatically, so visitor IP/source are captured.

### Option B — Docker (App Runner / ECS / any container host)

```bash
docker build -t stardust-landing ./landing
docker run -p 8000:8000 -v /srv/stardust-data:/app/data stardust-landing
```

For **AWS App Runner**: push the image to ECR and point App Runner at it. Mount
an EFS volume at `/app/data` (or use S3 export) so CSVs survive restarts.

### Option C — Elastic Beanstalk

`eb init`, choose the Docker platform, `eb create`, then `eb deploy`. Set the
`LANDING_DATA_DIR` environment variable to a persistent path.

> **Note on persistence:** CSV files vanish if the container/instance is
> replaced. For a 2-week experiment that's usually fine — but on App Runner/ECS
> mount EFS, or periodically copy `data/*.csv` to S3.

## View recorded leads — the admin console

Open **http://127.0.0.1:8000/admin** while the server is running. It shows:

- **KPI cards** — leads, unique visitors, conversion %, return rate, WTP votes.
- **Conversion funnel** — visits → ticker lookups → signal views → CTA clicks → email submits.
- **Traffic sources** and **top tickers requested** (with lead counts per source).
- **Leads table** — every email with ticker, source, and whether the visitor returned.
- **Events explorer** — filter by event type or search ticker/source/visitor.
- **Export** buttons for `signups.csv` / `events.csv`. Auto-refreshes every 15s.

The console is protected by a **PIN** (default `5073`). Enter it once and a signed
session cookie unlocks the data; the **Lock** button ends the session.

```bash
python landing/server.py
# open http://127.0.0.1:8000/admin and enter 5073
```

Override it with the `LANDING_ADMIN_PIN` environment variable if you want a
different PIN.

Always change the PIN before deploying, and set a fixed `LANDING_SECRET_KEY` so
sessions survive restarts (otherwise a new key is generated per process):

```bash
LANDING_ADMIN_PIN=2468 LANDING_SECRET_KEY=$(openssl rand -hex 32) \
  gunicorn --bind 0.0.0.0:8000 server:app
```

In production behind TLS, also set `LANDING_COOKIE_SECURE=1` so the cookie is
HTTPS-only. The PIN guards `/api/admin/data` and the CSV exports too — not just
the HTML page.

## What gets recorded

Two CSVs under `LANDING_DATA_DIR` (default `landing/data/`):

**`signups.csv`** — one row per conversion
`timestamp, email, ticker, source, utm_medium, utm_campaign, referrer, visitor_id, is_return, user_agent, ip`

**`events.csv`** — the funnel
`timestamp, event, ticker, source, visitor_id, is_return, path, referrer, meta`

Events: `visit`, `return_visit`, `ticker_lookup`, `signal_view`, `cta_click`,
`email_submit`, `wtp_yes` / `wtp_maybe` / `wtp_no`.

### Read the funnel

```bash
python - <<'PY'
import csv, collections
rows = list(csv.DictReader(open("landing/data/events.csv")))
c = collections.Counter(r["event"] for r in rows)
by_src = collections.Counter(r["source"] for r in rows if r["event"] == "email_submit")
print(dict(c))
print("email_submit by source:", dict(by_src))
signups = list(csv.DictReader(open("landing/data/signups.csv")))
print("signups:", len(signups))
PY
```

Compare against the thresholds in `VALIDATION_EXPERIMENT.md`:
`email_submit` ≥ 40, return-visit rate ≥ 20%, lookups/visitor ≥ 2.

Every link you post should carry a `?utm_source=` tag (e.g. `?utm_source=reddit_algotrading`),
which flows into both CSVs so you can attribute conversions.

## Before you launch — edit these

1. **`index.html` footer** — replace the "Who's behind this" line and the
   `anil.ojblabs@gmail.com` contact with your real details. Credibility without fake
   social proof.
2. **`app.js`** — optionally set `ANALYTICS.posthogKey` or
   `ANALYTICS.plausibleDomain` for third-party analytics (first-party still works
   without them).
3. **Ticker coverage** — regenerate `demo_signals.json` with the tickers you want
   to showcase. Any ticker not in the JSON still captures an email ("we'll send
   the report when ready"), so unknown tickers are not dead ends.
4. **Compliance language** — keep it as research/educational. Review the footer
   disclaimer before publishing.

## Tests

Unit + integration tests live in `landing/tests/` (no network, uses Flask's test
client and synthetic CSV/Parquet data):

```bash
pip install flask            # already in requirements.txt
python -m pytest landing/tests/ -q
```

Covered: CSV parsing, the admin summary math, PIN auth + session guard, the
signup/track/export endpoints, the demo lookup, the full visit→lead→WTP funnel,
and the demo-data generator's helpers (plus one integration run against real
AAPL data, auto-skipped if unavailable). A `landing-tests` pre-commit hook runs
these whenever `landing/` files change.

## A/B testing the headline (optional)

The single highest-leverage thing to iterate is the headline/problem framing. To
test one variant at a time, edit `index.html`, and split traffic with two UTM
sources — the `source` column then tells you which framing converts better.
Change one major assumption at a time (problem, audience, price, offer).
