# stardust landing page — signals experiment

A one-page, single-purpose landing site that tests whether S&P 500 investors will
trade an email for a stock's winning strategy + current buy/sell signal — and
whether they come back.

It is deliberately a **market experiment, not a website**:

- **Frontend:** static HTML/CSS/JS (no framework, no build step).
- **Backend:** one small Flask app that records signups and funnel events to SQLite.
- **Analytics:** first-party (your own database), tagged by traffic source. Optional
  PostHog/Plausible hooks in `app.js` if you want more.
- **Demo data:** generated by the real stardust engine, so the prototype numbers
  are honest — see `generate_demo_data.py`.

The experiment design, thresholds, and interpretation rules live in
[`../thermaltrend/VALIDATION_EXPERIMENT.md`](../thermaltrend/VALIDATION_EXPERIMENT.md).

## Deploying changes (the two commands)

After you merge to `main`, run these **on the server** (via the EC2 Instance
Connect browser session):

```sh
sudo git -C /root/stardust.git pull
sudo bash /root/stardust.git/landing/deploy/provision.sh
```

That's it — the first pulls the latest code, the second updates the app, restarts
`stardust-landing`, re-applies nginx and re-checks TLS, and leaves your data
(`landing.db`, `backups/`, `.admin.env`) intact. See
[Deploying changes (updates)](#deploying-changes-updates) for the full runbook
(what needs a restart, rollback, and the `/etc/gitconfig` gotcha).

## Updating the demo data

The page serves three committed JSON files. All are produced **offline** by
scripts — the server never runs the engine, it only reads the JSON:

| File | What it is | Regenerate with |
|------|------------|-----------------|
| `demo_signals.json` | Winning strategy per ticker × timeframe, OOS badge, current signal, latest close and each call's signal date/price/return-since | `generate_demo_data.py` |
| `demo_trades.json` | Actual completed trades behind each winning strategy (drill-down) | `generate_demo_data.py` |
| `tickers.json` | ticker → company name, powers company-name search | `generate_ticker_index.py` |

`generate_demo_data.py` writes `demo_signals.json` **and** `demo_trades.json` in
one pass (pass `--skip-trades` to skip the latter, or `--trades-output PATH` to
redirect it).

**When to update:** after refreshing price data (`thermaltrend/download_data.py`
or `thermaltrend/update_data.py`), after S&P 500 membership changes, or before a
(re)launch so the signals and names are current. All three files are committed, so
a refresh is just: regenerate → commit → redeploy. `demo_signals.json` records its
own `generated_at`, and every current signal carries an `as_of` date.

Run these **from the repo root** on a machine with the full repo + Parquet data
(the generators import `thermaltrend`):

```bash
# 1. Company-name index (fast). From the current S&P 500 membership table.
python landing/generate_ticker_index.py

# 2. Signals + trades for the whole S&P 500. Writes demo_signals.json and
#    demo_trades.json, checkpointing after every ticker. This is a FULL refresh,
#    so omit --resume (with it, an already-complete file is a silent no-op).
#    --workers parallelises across tickers: ~25 min sequential → ~2 min on 8
#    cores (output is byte-identical either way).
python landing/generate_demo_data.py --workers 8 \
  --tickers $(python -c "import json;print(' '.join(e['ticker'] for e in json.load(open('landing/tickers.json'))['tickers']))")
```

Useful flags for `generate_demo_data.py`:

- `--tickers AAPL NVDA KO` — a subset instead of the whole index.
- `--workers N` — run N tickers concurrently (default 1 = sequential). 0 or
  negative also means sequential. Per-ticker work is independent, so the output
  is identical; only wall-clock changes.
- `--skip-oos` — skip the out-of-sample holdout (much faster; drops the honesty badge).
- `--skip-trades` / `--trades-output PATH` — skip or redirect `demo_trades.json`.
- `--min-trades N` — minimum trades for a strategy to be recommended (default 3).
- `--resume` — keep tickers already in `--output`; **omit it to overwrite** the
  file with a fresh run (e.g. when you only want a specific subset). Note that
  `--resume` also skips already-present tickers for the trades file, so omit it
  when back-filling trades for a file generated before `demo_trades.json` existed.

Then commit `landing/demo_signals.json`, `landing/demo_trades.json` and
`landing/tickers.json` and redeploy (the Docker image bakes them in — see
`Dockerfile`).

### Automated daily refresh

`.github/workflows/refresh-demo-data.yml` runs every day at 03:00 UTC (≈10–11pm US
Eastern, after the close) and on manual **Run workflow**. It refreshes price data
(`update_data.py --strict`), regenerates the demo JSON for the whole universe,
runs the `landing/tests/` gate, and opens a `data/refresh-YYYYMMDD` pull request
with the refreshed `demo_signals.json` / `demo_trades.json` — only when the
content actually changed (ignoring `generated_at`, so weekends produce no PR),
and only when every ticker succeeded. Merge the PR and redeploy to publish it.

It commits **only** the JSON, not the ~195 MB of Parquet, to avoid bloating git;
the committed Parquet stays a periodically-refreshed baseline that each CI run
tops up from Yahoo. Scheduled workflows are auto-disabled after 60 days without
repo activity, so keep the repo active. New S&P 500 members remain a manual step
(`download_data.py` + the membership tables) — the daily job only refreshes prices
for tickers already present, and it does not rebuild `tickers.json`.

> A ticker missing from `demo_signals.json` (or without price data) is not a dead
> end: the page shows the "we don't have a cached report" message and still
> captures the visitor's email, so unknown tickers don't need any configuration.
> Likewise, a ticker present in `demo_signals.json` but absent from
> `demo_trades.json` still shows its metrics — it just can't expand into the
> trade-by-trade table.

## Deploy on AWS

The container is self-contained (Flask + gunicorn + static files). Pick one:

### Option A — EC2 provisioner (recommended; used for stardust.ojblabs.com)

`landing/deploy/provision.sh` is an idempotent **Amazon Linux 2023** provisioner.
It deploys only `landing/` (a sparse checkout) under `/opt/stardust`, runs it as a
`stardust-landing` gunicorn service behind nginx, issues a dedicated Let's Encrypt
cert, and installs a daily SQLite backup timer. It is built to coexist with other
sites on the same instance: it never installs Node and never rewrites the global
`nginx.conf`, so an existing `ojblabs.com` site is untouched.

**1. Point DNS at the instance.** In GoDaddy → *My Products → Domains → ojblabs.com
→ DNS*, add an **A** record `stardust` → the instance's Elastic IP (attach an
Elastic IP first, or the record breaks on stop/start).

**2. Run the provisioner on the instance:**

```bash
sudo git clone --depth 1 https://github.com/anilpank/stardust.git /root/stardust.git
sudo bash /root/stardust.git/landing/deploy/provision.sh
```

It prints the generated admin password once (stored hashed in
`/opt/stardust/landing/.admin.env`, mode 600). Override defaults with env vars:

```bash
sudo DOMAIN=stardust.ojblabs.com ADMIN_EMAIL=you@example.com ADMIN_PASSWORD='a-strong-password' \
  bash /root/stardust.git/landing/deploy/provision.sh
```

To ship a change after merging to `main`, see **Deploying changes (updates)** below.

**TLS:** Let's Encrypt certs are per-hostname, so an existing `ojblabs.com` cert
does **not** cover `stardust.ojblabs.com`. The script issues a separate cert for
`$DOMAIN` and reuses the existing `certbot.timer` for renewals. Only share one cert
if it is a wildcard `*.ojblabs.com`.

**Backups:** `stardust-landing-backup.timer` runs `deploy/backup_db.py` daily
(a `VACUUM INTO` snapshot, 14 kept) into `/opt/stardust/landing/backups`. Pull one
to your laptop with `landing/deploy/pull-db.sh`, or use the admin **Download DB**.

#### Deploying changes (updates)

**TL;DR — ship a change.** Merge to `main`, then on the server run:

```sh
sudo git -C /root/stardust.git pull
sudo bash /root/stardust.git/landing/deploy/provision.sh
```

The provisioner is **idempotent and re-runnable**: it fetches `origin/main`,
sparse-checks-out `landing/`, refreshes the venv from `requirements.txt`, rewrites
the systemd unit / nginx block / cert only when needed, and restarts the
`stardust-landing` service. The **one prerequisite** is that `/root/stardust.git`
is current — the provisioner you execute is the copy checked out there, so
`git pull` it first.

What each kind of change needs (all use the same two commands):

| Change | Notes |
|--------|-------|
| `index.html` / `styles.css` / `app.js` / `*.json` | Served from disk per request; the restart just makes it uniform. |
| `server.py` or anything in the venv | The service restart applies it. |
| `deploy/*.sh` or `deploy/*.py` | Pull `/root/stardust.git` **first**, since that is the script that runs. |
| Refreshed demo data | Regenerate + commit `demo_signals.json` / `tickers.json` first (see *Updating the demo data*). |

**Your data is safe across updates.** `landing.db`, the CSV exports, `backups/`,
and `.admin.env` live under `/opt/stardust/landing/` but are **git-ignored**, so
`git reset --hard` never touches them — the admin password persists and leads are
never lost. (They are *not* in git, so they also don't travel with a deploy.)

**Verify and roll back:**

```bash
curl -s https://stardust.ojblabs.com/api/health    # {"ok":true,...}
systemctl status stardust-landing
```

To roll back, revert on `main` and re-run the two commands, or deploy a known-good
branch by overriding `REPO_BRANCH`:

```bash
sudo REPO_BRANCH=stable bash /root/stardust.git/landing/deploy/provision.sh
```

> **If `git pull` fails with `git@github.com: Permission denied (publickey)`** the
> host rewrites GitHub https URLs to ssh via `/etc/gitconfig`. Root has an SSH key,
> so `sudo git … pull` normally works; if it does not, bypass the rewrite with:
> ```bash
> sudo env GIT_CONFIG_NOSYSTEM=1 GIT_CONFIG_GLOBAL=/dev/null git -C /root/stardust.git pull
> ```
> The provisioner itself already bypasses this rewrite when it clones/updates
> `landing/`, so only the manual root `pull` needs it.

### Option B — EC2 by hand (no provisioner)

```bash
# on the instance
sudo apt-get update && sudo apt-get install -y python3-venv
git clone <your-repo> && cd <your-repo>/landing
python3 -m venv .venv && . .venv/bin/activate
pip install -r requirements.txt

# run under systemd so it survives reboots
sudo tee /etc/systemd/system/stardust-landing.service >/dev/null <<'EOF'
[Unit]
Description=stardust landing
After=network.target
[Service]
WorkingDirectory=/home/ubuntu/<your-repo>/landing
Environment=LANDING_DATA_DIR=/home/ubuntu/<your-repo>/landing/data
# Admin Basic auth — generate with: python landing/gen_admin_password.py 'pw'
Environment=ADMIN_PASS_HASH=<salt>:<hash>
ExecStart=/home/ubuntu/<your-repo>/landing/.venv/bin/gunicorn --bind 127.0.0.1:8000 --workers 2 server:app
Restart=always
User=ubuntu
[Install]
WantedBy=multi-user.target
EOF
sudo systemctl enable --now stardust-landing
```

Put nginx in front for TLS (Let's Encrypt) and proxy `:80/:443` → `127.0.0.1:8000`.
`server.py` honours `X-Forwarded-For` automatically, so visitor IP/source are captured.

### Option C — Docker (App Runner / ECS / any container host)

```bash
docker build -t stardust-landing ./landing
docker run -p 8000:8000 -v /srv/stardust-data:/app/data \
  -e ADMIN_PASS_HASH='<salt>:<hash>' stardust-landing
```

For **AWS App Runner**: push the image to ECR and point App Runner at it. Mount
an EFS volume at `/app/data` (or export the DB to S3 regularly) so the SQLite
database survives restarts.

### Option D — Elastic Beanstalk

`eb init`, choose the Docker platform, `eb create`, then `eb deploy`. Set the
`LANDING_DATA_DIR` environment variable to a persistent path.

> **Note on persistence:** the SQLite DB vanishes if the container/instance is
> replaced. For a 2-week experiment that's usually fine — but on App Runner/ECS
> mount EFS, or periodically copy `data/landing.db` to S3. The admin console's
> **Download DB** button gives you a consistent snapshot any time.

## View recorded leads — the admin console

Open **http://127.0.0.1:8000/admin** while the server is running. It shows:

- **KPI cards** — leads, unique visitors, conversion %, return rate, WTP votes.
- **Conversion funnel** — visits → ticker lookups → signal views → CTA clicks → email submits.
- **Traffic sources** and **top tickers requested** (with lead counts per source).
- **Leads table** — every email with ticker, source, and whether the visitor returned.
- **Events explorer** — filter by event type or search ticker/source/visitor.
- **Export leads / Export events** download CSVs generated from the DB;
  **Download DB** downloads a consistent SQLite snapshot. Auto-refreshes every 15s.

The console is protected by **HTTP Basic auth** (same scheme as the `experiments`
repo): the browser prompts for a username and password, and the credentials are
re-checked on every request to `/admin` and `/api/admin/*`. There is **no default
password** — if none is configured, every login fails.

For local development, start the server with a plaintext password:

```bash
ADMIN_PASSWORD=secretpass123 python landing/server.py
# open http://127.0.0.1:8000/admin  (user: admin)
```

In production, set a **scrypt hash** instead of a plaintext password. Generate it:

```bash
python landing/gen_admin_password.py 'a-strong-password'
# ADMIN_PASS_HASH=<salt>:<hash>
```

Then pass it to the server (or your systemd unit):

```bash
ADMIN_PASS_HASH='<salt>:<hash>' ADMIN_USER=admin \
  gunicorn --bind 127.0.0.1:8000 --workers 2 server:app
```

`ADMIN_USER` defaults to `admin`. The `salt:hash` format matches Node's
`crypto.scryptSync` defaults, so the `experiments` repo's
`deploy/gen-admin-password.js` output works too. After **6 failed attempts** from
one IP, further logins are locked out for 5 minutes. Basic auth covers
`/api/admin/data`, the CSV exports, and the DB snapshot — not just the HTML page.

## What gets recorded

Everything lives in a single SQLite database — `landing.db` under
`LANDING_DATA_DIR` (default `landing/data/`). Two tables:

**`signups`** — one row per conversion
`id, timestamp, email, ticker, source, utm_medium, utm_campaign, referrer, visitor_id, is_return, user_agent, ip`

**`events`** — the funnel
`id, timestamp, event, ticker, source, visitor_id, is_return, path, referrer, meta`

Events: `visit`, `return_visit`, `ticker_lookup`, `signal_view`, `window_detail`,
`cta_click`, `email_submit`, `signal_unlock`, `wtp_yes` / `wtp_maybe` / `wtp_no`.

The DB is created automatically on first request (schema in `server.py`); no
migration step and no external service. Any pre-SQLite `signups.csv` /
`events.csv` in the data dir are imported once, on first boot, if the tables are
empty. The CSV files are now **exports only** (see the admin console), not the
source of truth.

### The signal gate (free history vs email-gated live call)

The demo shows the **full historical strategy fit** (1/3/5/10y + OOS badge) for
every ticker, to anyone — that's the trust engine. Each window card is a button:
click it to drill into the raw metrics behind the winner (win rate, total P&L,
CAGR, Sharpe, trades) **and the actual completed trades** (entry/exit, P&L, exit
reason) served lazily from `/api/trades`; expanding emits a `window_detail` event.
Each card also explains, in plain English, what the winning strategy *is* and what
its honesty badge means — and a collapsible glossary under the demo covers all six
strategies and both badge states. The result also shows the **analysis date**
(`generated_at`), and the demo header shows it up front from the preloaded
`/api/demo` response. The **live buy/sell call**
(the one actionable thing) is gated behind an email: `renderResult()` in
`app.js` renders a locked pill (`🔒 Live signal — unlock by email`) until signup.
On a successful `/api/signup`, the client unlocks it, emits a `signal_unlock`
event, and re-renders the current ticker's result. Unlock is client-side only
(persisted per browser via `localStorage.sd_unlocked`) — no accounts or server
gating, which is all a short experiment needs. To A/B the gate, split traffic by
`utm_source` and compare `email_submit` and `lookups/visitor`.

Unlocking also reveals the **price context**: the date the headline call first
appeared (`since`), the price it appeared at (next open after the signal, or the
signal day's close when there is no later bar), and the move since — sourced from
the committed backtest closes in `demo_signals.json`, not a live feed. The
per-window drill-down shows each window's own signal date/price/move, so it is
clear the windows did not all flip on the same day. A separate, **ungated**
`live` chip in the result header shows a delayed quote (`GET /api/quote`)
proxied from Yahoo Finance and cached ~60s server-side; it degrades silently when
Yahoo is unavailable. Quote and context are labelled as delayed/backtest so they
are not mistaken for a real-time feed.

### Read the funnel

```bash
python - <<'PY'
import sqlite3, collections
db = sqlite3.connect("landing/data/landing.db")
rows = [dict(r) for r in db.execute("SELECT event, source FROM events")]
c = collections.Counter(r["event"] for r in rows)
by_src = collections.Counter(r["source"] for r in rows if r["event"] == "email_submit")
print(dict(c))
print("email_submit by source:", dict(by_src))
print("signups:", db.execute("SELECT COUNT(*) FROM signups").fetchone()[0])
PY
```

Prefer a spreadsheet or the admin console? Use the **Export leads / Export
events** buttons (CSV) or **Download DB** (a consistent `VACUUM INTO` snapshot)
at `/admin`.

Compare against the thresholds in `VALIDATION_EXPERIMENT.md`:
`email_submit` ≥ 40, return-visit rate ≥ 20%, lookups/visitor ≥ 2.

Every link you post should carry a `?utm_source=` tag (e.g. `?utm_source=reddit_algotrading`),
which flows into both the signups and events tables so you can attribute conversions.

## A/B testing the headline (optional)

The single highest-leverage thing to iterate is the headline/problem framing. To
test one variant at a time, edit `index.html`, and split traffic with two UTM
sources — the `source` column then tells you which framing converts better.
Change one major assumption at a time (problem, audience, price, offer).
